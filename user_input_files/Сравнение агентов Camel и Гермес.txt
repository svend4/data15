для персонального AI-ассистента с долгой историей — Hermes;

Инструменты и MCP

Оба поддерживают MCP, но используют его по-разному.

Hermes использует MCP как расширение готового агента: он может подключаться к GitHub, databases, file systems, browser stacks, internal APIs и другим external tool servers через stdio/HTTP; tools автоматически обнаруживаются и регистрируются при старте. (Hermes Agent)
Итог по MCP:
CAMEL удобнее, если вы проектируете агентную архитектуру; Hermes удобнее, если хотите быстро дать уже работающему агенту доступ к внешним tool-серверам.

Интерфейс и удобство для пользователя

Hermes выигрывает по готовому UX. Он имеет terminal interface, TUI, slash commands, messaging gateway, работу через Telegram/Discord/Slack/WhatsApp/Signal/Email/Home Assistant, а также OpenAI-compatible API server для подключения к Open WebUI. (GitHub)
CAMEL выигрывает по developer control. Это Python-фреймворк: вы контролируете классы агентов, модели, toolkits, prompts, workflows, среды, benchmark-логику и интеграции.

Масштабирование и multi-agent research

CAMEL сильнее для multi-agent research. В README заявлены масштабируемость до систем с миллионами агентов, dynamic communication, benchmarks, разные agent types и world simulation/data generation/task automation как основные направления. (GitHub)
Hermes тоже умеет делегировать задачи subagents и запускать параллельные workstreams, но его фокус — practical autonomous assistant. Документация описывает subagent delegation, code execution, batch processing и scheduled tasks, но это часть продукта-агента, а не полноценная исследовательская multi-agent платформа уровня CAMEL. (Hermes Agent)

Когда выбрать CAMEL

Выбирайте CAMEL, если вам нужно:

создать свою multi-agent систему; проводить исследования; моделировать взаимодействие множества агентов; генерировать synthetic data; строить кастомные workflows; контролировать архитектуру на уровне Python SDK; подключать свои модели, tools, environments и evaluation pipelines.

Практический пример: «Нужно сделать систему из researcher-agent, planner-agent, coder-agent, reviewer-agent, benchmark-agent и собрать воспроизводимый pipeline». Здесь CAMEL логичнее.

готовый агент, который работает в терминале или мессенджерах; persistent memory; skills; terminal/file/browser/web tools; автоматизации по расписанию; подключение MCP-серверов без написания собственного агентного фреймворка; личный dev-assistant, который со временем накапливает контекст.

Практический пример: «Нужен агент на VPS, которому можно писать в Telegram, чтобы он проверял репозиторий, запускал команды, помнил предпочтения и делал регулярные отчёты». Здесь Hermes логичнее.

Риски и ограничения

CAMEL: выше порог входа, потому что это framework; нужно писать код, проектировать архитектуру, настраивать tools, memory, evaluation и безопасность самостоятельно. Он мощнее как основа для разработки, но не является «готовым персональным агентом из коробки».

Hermes: удобнее как готовый агент, но из-за терминала, файлов, browser automation, MCP и cron он потенциально получает широкий доступ к среде. Его стоит запускать в Docker/SSH/Modal/Daytona/sandboxed backend и внимательно настраивать инструменты, особенно если агент работает на сервере или с чувствительными файлами. Документация Hermes прямо описывает разные terminal backends, включая local, Docker, SSH, Singularity, Modal и Daytona. (Hermes Agent)

Итоговая рекомендация

Для продукта/исследования на базе multi-agent architecture — CAMEL.
Он лучше как фундамент: гибкость, масштабирование, роли, симуляции, data generation, MCP-as-client/server.

Для личного или командного AI-агента, который уже должен работать — Hermes.
Он лучше как готовый исполнитель: память, terminal, мессенджеры, skills, cron, MCP tools, TUI.

Самая точная формула:

CAMEL — чтобы строить агентов. Hermes — чтобы пользоваться агентом.

Похоже, вы имеете в виду Multica — репозиторий multica-ai/multica. Это действительно «из мира агентов», но она не совсем аналог CAMEL.

Главная формула:

CAMEL — фреймворк для создания multi-agent систем.
Hermes — самостоятельный AI-агент.
Multica — платформа управления агентами, как Linear/Jira/board для людей + AI-агентов.



То есть Multica не заменяет Hermes — она может управлять Hermes как одним из агентных backend’ов. И Multica не заменяет CAMEL — потому что CAMEL даёт SDK/архитектуру для разработки агентов, а Multica даёт рабочее пространство, задачи, доску, статусы, runtime’ы и командную координацию.

Что такое Multica

Multica — open-source платформа для управления coding agents: вы создаёте задачи, назначаете их агентам, следите за прогрессом, получаете комментарии, статусы, блокеры и историю выполнения. В описании проекта она позиционируется как managed agents platform: агенты становятся «участниками команды», которым можно назначать issues почти как человеку. (GitHub)
На сайте Multica прямо объясняется её отличие от простого запуска coding agent: обычный агент умеет выполнять работу, а Multica добавляет management layer — очереди задач, координацию команды, skill reuse, monitoring runtime’ов и единое представление того, что делает каждый агент. (Multica)

Как она работает технически

Архитектура Multica состоит из трёх частей:

Multica server — хранит workspaces, issues, members, task queue и agent definitions.
Daemon — маленькая программа на вашей машине, которая забирает задачи и запускает локальные AI coding tools.
AI coding tool — реальный исполнитель: Claude Code, Codex, Hermes, Gemini, OpenCode и другие. (Multica)
Очень важный момент: агенты не выполняются на серверах Multica. По текущей документации задачи исполняются через локальный daemon на вашей машине; ваши API-ключи, кодовые директории и toolchain остаются локально. Сервер Multica только координирует задачи и события. (Multica)
Типичный цикл такой: вы назначаете issue агенту, сервер ставит task в очередь, daemon забирает её, создаёт изолированную рабочую директорию, запускает выбранный AI coding tool, агент пишет код/запускает тесты/комментирует, а результат возвращается в Multica UI. (Multica)

Основные функции Multica

1. Агенты как участники команды

Агент в Multica — это почти полноценный member workspace: его можно назначить на issue, упомянуть в комментарии, он может отвечать, менять статус, создавать issues и быть project lead. Отличие от человека в том, что после assignment или @mention он стартует автоматически. (Multica)

2. Issues и board

Multica похожа на Linear/Jira/Trello, но с AI-агентами в роли исполнителей. Вы создаёте issue, назначаете его агенту, и агент сам начинает работу. События идут в timeline: кто назначил, что агент сделал, какие файлы читал, какие команды запускал, где застрял. (Multica)

3. Task lifecycle

Каждый запуск агента — это task. Он проходит состояния: queued, dispatched, running, completed, failed, cancelled. Есть timeout’ы, retry rules и manual rerun. Например, если task был dispatched, но не стартовал, timeout — 5 минут; если running слишком долго, timeout — 2.5 часа. (Multica)

4. Local daemon и runtimes

Daemon запускается на вашей машине и регистрирует runtime’ы. Runtime — это связка daemon × AI coding tool. Например, если на одной машине установлены Claude Code и Hermes, Multica может видеть разные runtime’ы и направлять задачи конкретному агенту. (Multica)

5. Поддержка многих coding agents

Multica поддерживает 10 AI coding tools. Но возможности у них разные: у одних есть session resumption, у других нет; MCP реально используется только Claude Code; skill injection paths тоже разные. Hermes в Multica поддерживает session resumption, но для skills используется fallback path .agent_context/skills/, поэтому документация советует проверять, действительно ли Hermes CLI читает этот путь. (Multica)

6. Skills

Skills в Multica — это knowledge packs на базе SKILL.md и дополнительных файлов. Их можно импортировать из GitHub, ClawHub, local directories или создать прямо в UI. Один skill можно прикрепить к нескольким агентам, и агент получает его при запуске задачи. (Multica)

7. Autopilots

Autopilots — это scheduled задачи для агентов. Можно задать cron expression и timezone, чтобы агент регулярно выполнял работу: отчёты, проверки, cleanup, standup summaries. Сейчас end-to-end usable triggers — schedule и manual; webhook/API triggers зарезервированы, но ещё не работают полноценно. (Multica)

Важные ограничения

Первое: Multica не является LLM-agent framework уровня CAMEL. Она не даёт вам такую же низкоуровневую архитектуру агентов, как CAMEL: роли, agent societies, simulation environments, synthetic data generation, research workflows. CAMEL для этого подходит лучше. (GitHub)
Второе: MCP в Multica сейчас фактически полезен только с Claude Code. Документация matrix прямо говорит, что из 10 tools только Claude Code реально читает mcp_config; остальные принимают поле, но игнорируют его. (Multica)
Третье: секреты надо хранить осторожно. В настройках агента можно задавать custom environment variables, но документация предупреждает, что значения custom_env хранятся в plaintext в server database; их не стоит использовать для production database passwords, root tokens и других high-value secrets. (Multica)
Четвёртое: third-party skills могут быть опасны. Multica не подписывает, не аудитит и не sandbox’ит imported skills; содержимое передаётся AI coding tool как есть, поэтому перед импортом из GitHub/marketplace нужно проверять SKILL.md и все файлы. (Multica)

Да — именно так можно построить архитектуру:

CAMEL сверху как “главный мозг / стратег / диспетчер”
Multica посередине как “операционный слой / task manager / board / runtime router”
Hermes снизу как “исполнитель задач / coding agent / terminal agent”



То есть ваша идея правильная: Multica может быть средним уровнем между CAMEL и Hermes.

Правильная схема

Пользователь / бизнес-цель
        ↓
CAMEL
главный multi-agent orchestrator:
планирует, разбивает задачу, выбирает исполнителя, проверяет результат
        ↓
Multica
средний слой:
issues, проекты, assignees, статусы, task queue, run history, runtime routing
        ↓
Multica daemon
локальный исполнительный слой:
видит доступные CLI-агенты и запускает нужного
        ↓
Hermes
конкретный агент-исполнитель:
пишет код, запускает команды, работает с файлами, памятью, tools/MCP

Это архитектурно даже очень естественно: CAMEL не должен сам запускать Hermes напрямую для каждой мелкой задачи, а может создавать задачи в Multica, назначать их Hermes-агенту, читать прогресс, добавлять комментарии и принимать решение, что делать дальше.

Почему это возможно

У CAMEL есть механизм tools: tool в CAMEL — это вызываемая функция, через которую агент получает доступ к внешним API, CLI или другой логике. То есть можно сделать CAMEL-tool, который вызывает Multica: создать issue, назначить его агенту, проверить runs, прочитать сообщения выполнения, добавить комментарий. В документации CAMEL tool описан как callable interface между агентом и внешним миром. (Camel AI)
У CAMEL также есть MCP-клиентский режим: CAMEL agent может подключаться к MCP servers через MCPToolkit, получать от них tools и использовать их как внешние возможности. Это значит, что самый чистый вариант — сделать или использовать Multica MCP server, а CAMEL будет управлять Multica через MCP. (Camel AI)
Со стороны Multica связка с Hermes уже предусмотрена: Multica daemon auto-detects agent CLIs, включая hermes, а при появлении задачи создаёт isolated workspace, запускает нужный agent CLI и стримит результаты обратно. (GitHub)В README Multica прямо указано, что она работает с Claude Code, Codex, OpenClaw, OpenCode, Hermes, Gemini, Pi и Cursor Agent. (GitHub)

Как это должно работать на практике

Например, пользователь даёт CAMEL большую задачу:

“Сделай аудит backend-проекта, найди проблемы авторизации, исправь их, добавь тесты и подготовь отчёт.”



CAMEL не обязательно сам лезет в репозиторий. Он делает план:

1. Проверить auth middleware
2. Найти слабые места в JWT/session logic
3. Добавить тесты
4. Исправить найденные баги
5. Проверить regression
6. Подготовить summary

Потом CAMEL через Multica создаёт несколько issues:

multica issue create \
  --title "Audit auth middleware" \
  --description "Check JWT/session/auth middleware for vulnerabilities..." \
  --priority high \
  --assignee "Hermes"

Multica ставит задачу в очередь. Daemon видит задачу, выбирает runtime с Hermes, запускает Hermes. Hermes выполняет задачу: читает код, правит файлы, запускает тесты, оставляет комментарии и статус.

Потом CAMEL читает результат:

multica issue runs <issue-id> --output json
multica issue run-messages <task-id> --output json

И решает:

— задача завершена хорошо → создать следующую
— тесты упали → вернуть Hermes уточняющую задачу
— найден риск → создать отдельный issue
— результат спорный → назначить reviewer agent / человека

Multica CLI уже поддерживает создание, назначение, обновление, комментарии, историю запусков и просмотр сообщений runs. В документации CLI есть команды multica issue create, multica issue assign, multica issue runs, multica issue run-messages и multica issue comment add. (GitHub)

Минимальный рабочий вариант без MCP

Можно проще: в CAMEL создать custom tool, который вызывает multica CLI.

Примерно так:

import subprocess
import json
from camel.toolkits import FunctionTool

def create_multica_issue(title: str, description: str, assignee: str, priority: str = "medium") -> str:
    """Create a Multica issue and assign it to an agent."""
    cmd = [
        "multica", "issue", "create",
        "--title", title,
        "--description", description,
        "--priority", priority,
        "--assignee", assignee,
    ]

    result = subprocess.run(
        cmd,
        capture_output=True,
        text=True,
        check=False,
    )

    if result.returncode != 0:
        return f"ERROR: {result.stderr}"

    return result.stdout

def get_multica_issue_runs(issue_id: str) -> str:
    """Get execution runs for a Multica issue."""
    cmd = ["multica", "issue", "runs", issue_id, "--output", "json"]

    result = subprocess.run(
        cmd,
        capture_output=True,
        text=True,
        check=False,
    )

    if result.returncode != 0:
        return f"ERROR: {result.stderr}"

    return result.stdout

create_issue_tool = FunctionTool(create_multica_issue)
get_runs_tool = FunctionTool(get_multica_issue_runs)

Потом CAMEL-agent получает эти tools и может сам создавать задачи в Multica. CAMEL docs прямо показывают, что custom Python function можно wrapped as FunctionTool и передать в ChatAgent. (Camel AI)

Роли в такой системе

Самая важная часть — не смешивать роли.

Слой Роль Что должен делать
CAMEL Главный orchestrator Декомпозиция задач, выбор стратегии, контроль качества, re-planning
Multica Операционный middle layer Issues, board, статусы, очереди, runtime routing, история выполнения
Hermes Исполнитель Кодинг, терминал, файлы, тесты, локальные tools, skills, память
Человек Владелец/ревьюер Утверждение рискованных действий, merge, production-доступ

В такой модели CAMEL управляет не Hermes напрямую, а работой через Multica. Это лучше, потому что Multica сохраняет историю, статусы, контекст задачи, комментарии и execution logs.

Где Multica действительно “средний уровень”

Multica здесь выполняет роль, похожую на:

Jira / Linear / Trello + agent runtime router + execution monitor

Она не столько “думает”, сколько организует работу:

кто делает → что делает → где выполняется → какой статус → что сказал агент → какой результат

CAMEL может быть “главным менеджером”, но Multica — это “операционная система команды агентов”.

Важное ограничение

Связка Multica → Hermes есть, но Hermes-интеграция в Multica ещё может быть менее зрелой, чем, например, Claude Code. В changelog Multica указано появление Hermes Agent Provider via ACP protocol 10 апреля 2026. (Multica)При этом на GitHub были недавние закрытые issues, где пользователи сообщали о проблемах Hermes-интеграции: например, один issue от 23 апреля 2026 описывал, что Hermes поддерживается, но не полностью интегрирован с meta skills/skill resolution; другой issue от 16 апреля 2026 описывал сбой Hermes с local LLM provider. Поскольку оба issue отображаются закрытыми, это не доказательство текущей поломки, но это сигнал: перед production-схемой нужно протестировать конкретные версии Multica и Hermes. (GitHub)

Иначе CAMEL + Multica + Hermes превращаются в цепочку, где верхний агент может косвенно заставить нижний агент делать слишком много.

Идеальная логика цикла

1. CAMEL получает цель.
2. CAMEL разбивает цель на задачи.
3. CAMEL создаёт issues в Multica.
4. CAMEL назначает issue на Hermes.
5. Multica daemon запускает Hermes.
6. Hermes выполняет задачу.
7. Multica собирает output, status, comments, logs.
8. CAMEL читает результат.
9. CAMEL принимает решение:
   - принять;
   - отправить на доработку;
   - создать новую подзадачу;
   - назначить reviewer agent;
   - попросить человека вмешаться.

Это уже похоже на агентную организацию, где CAMEL — “руководитель”, Multica — “операционный офис”, Hermes — “сотрудник-исполнитель”.

Короткий ответ

Да, можно:

CAMEL управляет Multica. Multica управляет Hermes. Multica является средним уровнем между CAMEL и Hermes.



Но точнее сказать так:

CAMEL — стратегический orchestration layer.
